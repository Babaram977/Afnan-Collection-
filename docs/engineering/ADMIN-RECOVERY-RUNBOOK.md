## Routine login and sensitive changes

Email authentication creates a customer-capable primary session, not an administrator session. The owner completes WebAuthn to receive a one-hour/15-minute-idle privileged proof. Backup-key enrollment requires WebAuthn verification within five minutes. Sign out of administration revokes the current primary/proof sessions; general account sign-out also invalidates the primary session and therefore any bound administrator proof. To revoke all access, the operator must remove the staff role or mark admin_security disabled and increment epoch under separately approved, audited D1 operations. Reassignment to an active identity requires a new reviewed activation decision; never use email alone as proof.

## Lost authenticator with recovery code

1. Use the trusted origin, authenticate again with a new email code and provide one offline recovery code within five minutes. Confirm the requested recovery under the owner's approved verification policy; for sensitive manual assistance obtain the independent verifier's per-action confirmation.
2. The server atomically advances security epoch to recovery, consumes the old code set, removes all registered keys and revokes all primary sessions. No administration privilege is granted. Failure leaves access denied; inspect audit IDs without logging the supplied code.
3. Owner signs in with another fresh email code and personally enrolls a replacement verified authenticator. Only then is a new privileged session issued. Save the new once-shown code set; old codes/keys never restore access. Verify logout/revocation and backup enrollment. Record completion privately.

## Loss of all authenticators and codes / suspected compromise

There is no public MFA-reset endpoint. Stop access first: the authorized operator, after explicit incident authorization, marks the Afnan admin security state disabled, increments epoch and deletes the affected primary/proof/challenge sessions. Do not weaken the shared IdP, invite a substitute email or alter another business. Verify the owner and specific reset request independently through the nominated human verifier and known trusted channels; require mailbox recovery/control before continuing. Record operator, time, outcome and owner approval reference in restricted audit storage.

A separately approved D1 reset must invalidate all keys, recovery codes, sessions and challenges; update the verification/approval references; move only the exact verified identity to pending; insert `admin.mfa.manual_reset` audit evidence. Review all SQL predicates against the exact user ID/database before execution. No generic runnable reset is supplied because it would bypass the required human verification gate. Owner must reauthenticate email and enroll new MFA before any privileged access. If ownership cannot be established, remain locked out. If the operator also loses Cloudflare access, use account-owner Cloudflare recovery/support; never disable MFA globally or create emergency storefront admins.
